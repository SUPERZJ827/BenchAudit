# Workspace grounding P0 独立复核协议

协议版本：`workspace-grounding-p0-adjudication-v1-20260728`

## 1. 目标

本轮不修改模型、prompt、router、verifier 或既有实验输出，也不调用新的
DeepSeek API。目标是回答：

1. 双视角新增的 review-only candidates 中有多少是真正的 grounding
   defect；
2. verifier 是否系统性地把 intrinsic validity、通用质量标准或可推导要求
   错判为 unsupported；
3. 既有 reviewed-positive 中的漏检应由哪个 detector family 负责；
4. 后续 routing、detector 和 system-union 指标应使用什么分母。

## 2. 冻结输入

- 双视角 holdout：
  `experiments/workspace_grounding/DUAL_TRIAGE_HOLDOUT_30_20260728.json`
- 双视角逐 rubric 结果：
  `reports/workspace_grounding_dual_triage_holdout30_20260728/grounding_dual_triage_items.jsonl`
- reviewed reference：
  `WorkspaceBench_full388_Codex证据化逐条标注_20260720.md`
- 数据集：
  `datasets/workspacebench/full.jsonl`

生成器必须在 receipt 中记录上述文件的 SHA256。任何输入哈希改变都需要生成
新的协议版本，不能覆盖本轮结果。

## 3. 复核单位与 37 条构成

复核单位是唯一 `(item_id, rubric_index)` candidate，不按 finding 行计数。

重点案例共 17 条：

1. 全部 13 条 `support_challenge-only + final unsupported`；
2. 全部 4 条已有 reviewed-positive、但两个 triage view 均未路由的案例。

对照共 20 条：

1. 从 `support_challenge-only + final supported` 中抽 10 条；
2. 从 `support_challenge-only + final uncertain` 中抽 10 条。

对照抽样种子固定为：

`workspace-grounding-p0-blind-v1-20260728`

抽样规则：

1. 排除 17 条重点案例涉及的 task；
2. 每个 outcome stratum 先按 task 去重，每个 task 最多抽一条；
3. 对候选的 `(item_id, rubric_index)` 稳定排序后，用固定种子打乱；
4. 若 task 去重后不足 10 条，再从剩余 candidate 中按同一随机序补齐；
5. blind id 由协议版本、item id、rubric index 的 SHA256 前 12 位生成；
6. 最终 blind package 按 blind id 排序，不保留重点/对照、A/B、旧 verdict、
   reviewed label 或 detector 输出。

## 4. 复核字段

每条必须填写：

```text
grounding_class:
  hidden_exact_constraint
  intrinsic_validity
  general_quality
  task_or_input_derived
  task_contract_conflict
  insufficient_evidence

is_grounding_defect:
  yes | no | uncertain

evaluation_objectivity:
  objective | subjective | mixed | uncertain

satisfaction_checkability:
  static | artifact_execution | llm_judge | human_review | mixed | uncertain

primary_family:
  one detector family

acceptable_families:
  zero or more detector families

root_cause_summary:
  concise description

evidence:
  exact task/contract/input quote and source

confidence:
  0.0--1.0
```

`acceptable_families` 是集合，不能为了计分强制唯一归属。后续另行构造
`root_cause_id` 和 `one_fix_cluster_id`，同一修复能消除的多个 rubric finding
只计一个 unique root cause。

## 5. 判定边界

### task/input 可推导

只有同时满足以下条件才能判为 grounded：

1. 所需信息确实存在于允许证据；
2. 推导规则基本唯一；
3. rubric 没有额外引入过滤、舍入、统计口径或 tie-break；
4. 不依赖不可见 candidate output 来证明 requirement 的来源。

### 合法通用质量标准

必须分别判断：

1. rubric requirement 是否合理；
2. requirement 是否客观；
3. 当前 output 是否满足 requirement。

“清晰、专业、无明显错误”等通常不是自动 benchmark defect，但可能需要
LLM/human judge。没有 candidate output 只能阻止第 3 项裁决，不能自动把
第 1 项判为 unsupported。

### intrinsic validity

“文件应能打开”“格式有效”“请求的 artifact 应存在”属于合法 requirement。
grounding 结论只能是 requirement 合法，不得伪装成已经执行并验证当前 artifact。

## 6. 独立性与冲突处理

- Claude：第一位真正的 blind annotator，只接收 blind package 和本协议，
  不接收 sealed mapping、既有 verdict 或来源 stratum。
- Codex：由于已经在协议设计阶段看过部分重点案例，只能作为
  `non_blind_evidence_review`，不能声称 blind 或 independent ground truth。
- 两者一致：记为 `reviewed_agreement`，仍不是 human gold。
- 两者分歧：保持 `adjudication_conflict`，不强制多数票，不进入硬
  precision/recall 分母；如有人力，仅将冲突项交给人审。

报告原始一致率；样本足够时补充 Cohen's kappa，但不以显著性作为硬 gate。

## 7. 后续指标

至少分别报告：

1. routing recall：应进入某 detector 的案例中，有多少被路由；
2. detector precision/recall：进入 detector 后裁决是否正确；
3. system-union recall：是否被任一 acceptable family 合法发现；
4. logical calls / unique reviewed root cause；
5. incremental calls / incremental reviewed root cause；
6. 未标注、冲突和 operational unknown 数量。

不能让 system union 掩盖单个 detector 的退化，也不能把未标注候选自动计作
TP 或 FP。

## 8. 版本纪律

1. 本协议必须在 blind package 生成前提交；
2. package receipt 和盲包单独提交；
3. 第一位 annotator 完成后才可揭示 source mapping；
4. 第二批 30 题从此视为开发数据，不能用于证明下一版泛化；
5. P0/P1 完成前不修改 GroundingDecisionContract 或 exact router；
6. 第三份 holdout 必须在代码、contract、规则、指标全部冻结后生成。
