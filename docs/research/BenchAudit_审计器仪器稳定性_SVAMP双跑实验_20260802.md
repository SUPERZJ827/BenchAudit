## 0. 一句话

> 在**代码完全相同**（`benchcore/` diff = 0 行）、模型、温度、配置、输入哈希、题目清单全部相同的两次运行之间，SVAMP 审计的 **F1 从 0.750 变到 0.707，逐条 finding 只有 54% 能复现**；其中确定性检查器复现率 **100%**，全部 LLM auditor 落在 **0.44–0.82**。

这不是回归，是**噪声**。而这个噪声大到足以让我们过去所有"跨版本单跑对比"的结论失效——包括我自己在 07-31 规划里写的那条。

值得注意的是：`llm_question_clarity` 和 `llm_gold_audit` 复现率最低（0.44），而它们恰好是 07-07→07-30 之间假阳增长最多的两个（分别 +5 和 +3）。**假阳增长集中在最不可复现的 auditor 上。**

## 3. 机制：为什么温度 0 也会这样

不是"LLM 有随机性"这么笼统。机制是**答案依赖的 prompt 级联**，在代码里可以精确指出：

```python
# benchcore/llm_auditor.py:1047
def build_gold_evidence_user_prompt(
    item, blind_solution, option_matching=None, option_evidence=None,
):
    payload = common_item_payload(item)
    payload["blind_solution"] = blind_solution      # ← 上一次 LLM 的回答被写进下一个 prompt
    ...
```

而缓存键覆盖 `user` 文本（`llm_client.py:411-427`），所以：

```
盲解 LLM 调用（provider 在 temperature=0 下并非逐位确定）
  → 回答文本略有不同
  → 被嵌入下一个 gold-evidence prompt
  → 下游 prompt 文本变了 → 缓存键变了 → 是一次全新的调用
  → 而且 blind_solution_is_risky / defender_is_needed / option_evidence_is_risky
    这些门控函数还会决定后续调用「要不要发生」
  → 一次上游抖动扇出成一批下游差异
```

实测扇出规模：两次运行的缓存键交集只有 **400 / 664 ≈ 60%**，即**约 40% 的 LLM 调用在两次运行中根本不是同一次调用**——在代码、模型、配置、数据全部相同的情况下。

这也解释了 §2.1 里"精度稳、召回不稳"的形态：级联影响的是**是否发起后续审查**，而不是既有证据的判读标准。

## 4. 一个方法学发现：跨 2026-07-16 的"同缓存重放"不可能

我原计划用"同一份缓存 + 不同代码版本"把模型因素排除掉做 bisect。这个方法在 07-16 这条线上不成立：

```
commit ac99446  (2026-07-16)  Add adaptive benchmark auditing and objective evidence replay
  → benchcore/llm_client.py 的 _cache_key() 新增 "thinking": self.config.thinking
```

缓存键是整个 payload 的 SHA-256，新增一个字段就让 **07-16 之前写入的每一条缓存永久不可达**。实测 0707 缓存（648 条）与 0730 缓存（661 条）**键交集 = 0**。

这个 0 交集**不能**用来推断模型或 prompt 变了——它被键组成变更完全解释。（我在中期结果里差点据此得出错误推论，是在核对 `ac99446` 时截住的。）

对应的修复要求已写进 V3 指令 R4：给缓存键加 `CACHE_KEY_SCHEMA_VERSION` 并记入缓存行与 run_metadata。

## 5. 对 0.900 → 0.750 那个问题的回答

原问题："为什么 07-07（F1 0.900）到 07-30（0.750）掉了 0.15？"

**现在的回答是：这个问题在当前证据下不可回答，而且提问方式本身有问题。**

- 同代码复现的 F1 落差已经有 **0.043**（n=2），逐条 finding 一致性只有 **0.545**；
- 0.15 的落差约是观测到的单次噪声跨度的 3.5 倍，所以**可能**含真实成分，但**单跑对单跑不足以归因**；
- 07-16 的缓存键变更又切断了跨该日期的同缓存对照；
- 因此：要回答它，必须**每个版本跑多次**取分布，而不是每个版本跑一次比大小。

这也意味着：**我们过去所有"某某改动让 F1 提升/下降了 X"的单跑结论，都需要重新标注为不可归因**，除非该改动影响的是确定性路径。

## 6. 对项目的三条实际影响

**(1) 这是一个可发表的独立发现，而且是负面但诚实的那种。**

综述覆盖的 80 篇文献里，普遍报告 top-k precision，**没有一篇报告审计器自身的 run-to-run 稳定性**。我们能报：同代码同配置双跑，逐条 finding 复现率 0.54，确定性层 1.00、LLM 层 0.44–0.82。这不需要新实验，产物已经在仓库里。

**(2) 它把"confirmed 必须确定性"从设计信条变成了实测结论。**

以前这是一个论证（"LLM 判断不可重放"）。现在是一张表：确定性方法 100%，LLM 方法最低 0.44。这是全项目最有说服力的一张图之一。

**(3) 它给出了具体的工程改进方向，而且是可验证的。**

- 复现率最低的三个（`llm_question_clarity`、`llm_gold_audit`、`llm_quantity_consistency_nonmaterial`，均 0.44）应优先加投票或提高触发门槛；历史数据表明 vote3 能把 SVAMP 候选召回推到 1.000（`RESULTS.md`），代价是精度；
- 答案依赖的级联是不稳定性的放大器。可以考虑把嵌入下游 prompt 的 `blind_solution` **规范化**（只传结构化结论，不传自由文本），减少扇出；
- 任何报告都应附"该指标基于 n 次运行"，n=1 时明确标注不可归因。

## 7. 诚实边界

- **n=2。** 这是一个跨度，不是方差估计。要给区间需要至少 5 次重复。
- 两次运行相隔两天，provider 侧的模型服务是否在此期间有变化，我们无法从本地产物判断——所以严格说这是"同代码、同声明模型、跨两天"的复现，不是同一时刻的重复采样。**要排除这一点，需要同一天内连跑多次。**
- 07-30 那次有 32 条缓存命中（来自更早的缓存），08-01 是全新缓存（0 命中）。这使 07-30 有一小部分调用是复用的，属于轻微不对称。
- 0707 与 0730 之间的落差仍未归因，且按 §4 无法用同缓存方法归因。
- 本文没有逐条判读那 17 个假阳是"系统错"还是"Platinum 漏标"。07-07 时代的 6 个假阳里有 4 个曾被判为"真问题但 Platinum 未标"（`RESULTS.md`）；若该比例保持，实际精度损失会小于表面数字。**这一项尚未做。**

## 8. MMLU 侧的检查：没有干净的复现对，但核心分离得到复制

我原打算把同一分析套到 MMLU 上，回答"为什么 SVAMP 不稳而 MMLU 稳"。**结论是：仓库里不存在干净的 MMLU 复现对**，因此不能给出 MMLU 的噪声量级。

- `audit_full1000`（历史）与 `mmlu1000_report`（08-01）：`input_sha256` 不同（`70cc9ee1…` vs `78eabb78…`，属已记录的 MMLU 输入更正），method 数 17 vs 18 → **不可比**；
- `mmlu200` 与 `mmlu200_comparable`：输入哈希与题目 manifest **完全相同**（`0c8ccf09…` / `1922ee18…`），模型与投票设置相同，但 method 集合是 21 vs 18（`comparable` 臂刻意剔除了 `llm_event_state`、`llm_quantity_consistency`、`llm_presentation_integrity` 以对齐历史）→ **这是有意的配置差异，不是复现**。

因为 `auditor.py` 存在跨方法的 LLM evidence fusion，剔除三个方法会影响其余方法的输入，所以这一对的整体一致性（0.21）**不能**当作 MMLU 的噪声估计。

不过有一件事在这个被污染的对照里依然成立，而且正因为被污染才更有力——**确定性方法仍然逐条精确复现**：

| detection_method | mmlu200 | comparable | 两次都有 | 复现率 |
|---|---:|---:|---:|---:|
| `static_rule` | 1 | 1 | 1 | **1.00** |
| `task_integrity_rule` | 4 | 4 | 4 | **1.00** |
| `llm_evidence_fusion` | 37 | 57 | 32 | 0.52 |
| `llm_gold_audit` | 104 | 73 | 47 | 0.36 |
| `llm_option_set` | 75 | 26 | 17 | 0.20 |
| `llm_question_clarity` | 61 | 18 | 12 | **0.18** |

在一个 LLM 层被扰动到 0.18–0.52 的条件下，两个确定性方法仍是 1.00。**§2.3 的核心分离在第二个 benchmark 上得到复制。**

另有一个跨数据集一致的次级信号：`llm_question_clarity` 与 `llm_gold_audit` 在 SVAMP 上是最差的两个（均 0.44），在 MMLU 上仍是最差之列（0.18 / 0.36）。**同两个 auditor 在两个 benchmark 上都最不稳定**——这使"优先给这两个加投票或提高触发门槛"从猜测变成有依据的排序。（受本节确认的混淆影响，量级不可引用，排序可引用。）

## 10.5 按预注册解读规则的裁定

协议 §4 写定的三条，逐条裁定：

1. F1 极差 **0.046 ≥ 0.02** → **确认**：审计器输出在完全固定的条件下具有实质性运行间波动，`n=1` 的跨版本对比不可归因。
2. 确定性方法复现率必须为 1.00 → **满足**（`static_rule` 1.00、`cross_artifact_consistency` 1.00）。
3. 无需触发"重新审视 07-30/08-01 差异"的分支——但见 §10.6，那条差异确实需要单独解释。

## 10.6 **必须更正的数字**：0.545 高估了纯不确定性

§2.2 报告的 violation 级 Jaccard **0.545** 来自 07-30 与 08-01 的**跨日**配对。同日 n=5 的 10 个配对给出的是 **0.845（min 0.796）**。

**因此 §2.2 的 0.545 不能作为"审计器的运行间复现率"引用。** 正确的拆分是：

| 成分 | violation Jaccard |
|---|---:|
| 同日、同代码、同配置的纯不确定性 | **0.845** |
| 07-30 ↔ 08-01 跨日配对 | **0.545** |

两者相差 0.30，**远超同日配对自身的跨度（0.796–0.913）**。也就是说：跨日那次的不一致里，有一大部分**不是**同日噪声能解释的。

可能来源（本实验无法区分，需另做实验）：

- provider 侧模型服务在 07-30 到 08-01 之间发生了变化（同名模型、不同权重或不同解码栈）；
- 07-30 那次有 32 条缓存命中（来自更早的缓存），并非全新缓存；
- 07-30 与 08-01 的 `--workers` 取值未记录，可能与本次的 8 不同。

**这本身是一个更值得报告的发现**：审计器有一个同日噪声底（violation 级 0.845），此外还有一个**更大的跨日漂移成分**。前者是模型采样不确定性，后者更像是测量仪器的**校准漂移**。任何跨日、跨版本的对比都同时受这两者影响，而后者更大。

同时注意：**F1 的极差在两种情况下几乎相同**（同日 0.046，跨日 0.043）。也就是**聚合指标完全掩盖了成分漂移**——两天的 F1 看起来差不多，但具体是哪些 finding 变了差异巨大。这对"用单一 F1 比较不同版本"是一个直接的反例。
